# Rust

Rust code compiles into `ns-slapd` and three server plugins. The cargo workspace root is `src/Cargo.toml` — not the repo root. Every member crate declares `rust-version = "1.70"` and `edition = "2018"` in its own `Cargo.toml` (for example src/librslapd/Cargo.toml). That declaration is not a verified MSRV: the Rust workflow uses the toolchain from a floating Fedora image and has no 1.70 lane (`.github/workflows/cargotest.yml` (`rust-tests`)). The current lock records `uuid` 1.24.0, whose package metadata requires Rust 1.85; that recorded selection is incompatible with a 1.70 floor (`src/Cargo.lock` (`uuid` package entry)). Re-check dependency MSRVs after every lock refresh. `src/svrcore`, `src/libsds` and `src/rewriters` are C code under `src/`, not workspace members.

`slapi_r_plugin` is the Rust-facing wrapper over SLAPI (`SlapiPlugin3`, `PblockRef`, `EntryRef`, ... re-exported through `slapi_r_plugin::prelude`); it is not a memory-safety boundary. Its wrappers depend on the same raw-pointer, lifetime, ownership and C-layout contracts as their SLAPI calls. The `slapd` crate is the only no-FFI crate and is where real logic belongs. How a Rust plugin becomes a loadable `.so` (the `init.c` shim, the `<mod>_plugin_init` naming contract): [plugins.md](plugins.md).

## Hard facts

- The workspace `[profile.release]` sets `panic = "abort"` and `lto = true` (src/Cargo.toml (`[profile.release]`)): a Rust panic in a release build aborts the whole `ns-slapd` process. A debug build normally unwinds within Rust, but a panic that reaches any non-unwinding `extern "C"` export also terminates the process; this includes generated plugin callbacks and exports from `librslapd` / `librnsslapd` (`src/slapi_r_plugin/src/macros.rs` (`slapi_r_plugin_hooks!`), `src/librslapd/src/lib.rs`, `src/librnsslapd/src/lib.rs`). Treat every C ABI entry point as panic-free. Failures caused by LDAP values, configuration, task arguments or other runtime-controlled input must propagate as `Result` / `PluginError` and become the callback contract's explicit failure form, such as an LDAP/plugin code or NULL pointer; a void callback must log and clean up without panicking. Do not use `panic!()`, `unwrap()`, `expect()` or indexing without a prior bounds check on those paths.
- `#![deny(warnings)]` is line 1 of `librslapd`, `librnsslapd`, `slapi_r_plugin` and `pwdchan` — any new warning there is a hard build failure. Not set in `slapd`, `entryuuid`, `entryuuid_syntax`.
- Rust is not optional. `configure.ac` has no `--enable-rust` flag; only `--enable-rust-offline` exists, and it merely switches to vendored/offline mode. `configure` probes for `cargo`/`rustc` only under that flag, so a plain `./configure` succeeds with no Rust toolchain and the build fails later in `make`.

## FFI boundary

- Every `*Ref::new` constructor that accepts a raw C pointer through a safe Rust signature depends on invariants it does not validate: nullness, provenance, type, liveness and ownership. Current examples include `PblockRef`, `EntryRef`, `SdnRef`, `ValueArrayRef`, `ValueRef`, `BerValRef` and `TaskRef` (`src/slapi_r_plugin/src/pblock.rs (PblockRef::new)`, `entry.rs (EntryRef::new)`, `dn.rs (SdnRef::new)`, `value.rs (ValueArrayRef::new, ValueRef::new)`, `ber.rs (BerValRef::new)`, `task.rs (TaskRef::new)`). Treat constructing any such wrapper as an unsafe operation despite the current signature: prove the pointee is the expected SLAPI object, keep borrowed wrappers inside the C object's documented lifetime, and never free a borrow. Callback-borrowed objects normally cannot be retained after the callback; extend a lifetime only when a documented ownership contract explicitly permits it. `ValueRef::new` immediately dereferences its argument, and `BerValRef::into_cstring` creates a slice from C-provided pointer/length. Violating one of these invariants is undefined behavior and may crash the server or corrupt memory rather than returning an ordinary Rust error.
- The C headers are generated by cbindgen from each stub crate's `build.rs`, and only when `SLAPD_HEADER_DIR` is set — a bare `cargo build` writes no header. Header naming is crossed: `librslapd` emits `rust-slapi-private.h`, `librnsslapd` emits `rust-nsslapd-private.h` (src/librslapd/build.rs, src/librnsslapd/build.rs).
- `SLAPD_DYLIB_DIR` gates linking: `src/slapi_r_plugin/build.rs` emits `-l slapd` plus the link-search paths only when it is set. Anything that invokes the linker — notably `cargo test` on the plugin crates — fails on unresolved `slapi_*` symbols without it; plain `cargo build` (staticlib/rlib) defers symbol resolution and is unaffected.
- There is no bindgen anywhere in the workspace. `src/slapi_r_plugin/src/constants.rs` (`PluginFnType`) hand-duplicates the numeric `SLAPI_PLUGIN_*_FN` values from `ldap/servers/slapd/slapi-plugin.h`, `src/slapi_r_plugin/src/ber.rs` (`ol_berval`) and `value.rs` (`slapi_value`) hand-duplicate C layouts, and the wrapper's SLAPI entry points are handwritten in `extern "C"` blocks. A change in a C declaration or layout does not propagate to Rust; compare both sides whenever either changes. One current mismatch demonstrates the risk: Rust declares `slapi_value.v_flags` as `u32`, while C declares it as `unsigned long`, which is 64 bits on LP64 targets such as x86_64 Linux (`src/slapi_r_plugin/src/value.rs (slapi_value)`, `ldap/servers/slapd/slap.h (struct slapi_value)`). Do not treat that copied definition as layout-verified; its field width must be reconciled in a separate code change.
- The stub crates state their own rule at the top of `src/librslapd/src/lib.rs` and `src/librnsslapd/src/lib.rs`: symbol names must be unique across both crates, and all logic should come from the `slapd` crate. Adding a symbol to one means checking the other.
- Adding a new kind of plugin hook takes three coordinated edits in `src/slapi_r_plugin/src/`: the `SlapiPlugin3` trait (`plugin.rs`), the `slapi_r_plugin_hooks!` macro (`macros.rs`), and a `register_*_fn` method on `PblockRef` (`pblock.rs`).

## Build wiring

- Cargo is invoked from the top-level `Makefile.am`, one `cargo rustc` rule per artifact (targets of the form `rs/<name>/@rust_target_dir@/lib<name>.a`); the plugin rules also copy the `.a` into `.libs/` so the `-l<name>` link flags resolve. Do not add cargo invocations anywhere else.
- Every compiling cargo invocation sets `RUSTC_BOOTSTRAP=1` so a stable rustc accepts the `-Z` flags that the debug and sanitizer profiles pass (set on every cargo rule in the top-level `Makefile.am`; the `-Z` flags come from `configure.ac`). Dropping it breaks debug and sanitizer builds.
- Each rule sets a per-crate `CARGO_TARGET_DIR` under the build tree's `rs/`; a bare `cargo` run outside autotools writes `src/target` instead (gitignored).
- A new `.rs` file in `src/slapi_r_plugin/src/` must be added to `libslapi_r_plugin_SOURCES` in `Makefile.am`, or the three plugin `.a` targets will not rebuild when it changes. `modify.rs` is currently missing from that list — rebuilds silently skip edits to it.

## Tests

- `.github/workflows/cargotest.yml` is the only Rust CI: `autoreconf -fvi`, `./configure --enable-debug`, `make`, `make check-local`. No workflow runs a bare `cargo` command.
- `check-local` (Makefile.am) tests only `librslapd`, `librnsslapd` and `plugins/pwdchan`; `slapd`, `slapi_r_plugin`, `entryuuid` and `entryuuid_syntax` are never `cargo test`ed. The pwdchan run passes `--features=slapi_r_plugin/test_log_direct` so logging does not require a live `libslapd`.
- Under `--enable-rust-offline` or `--enable-asan`, `check-local` is an empty automake stub: it exits 0 having run nothing. RPM builds configure with `--enable-rust-offline` (rpm/389-ds-base.spec.in), so the Rust unit tests run only in the cargotest job — see [building.md](building.md) for the RPM path.
- Each `check-local` loop writes its command twice: the first copy is `echo`-prefixed and only prints, the second executes. Editing only the printed copy changes nothing.
- Behaviour coverage for the Rust plugins is pytest, not cargo: `dirsrvtests/tests/suites/entryuuid/` and `dirsrvtests/tests/suites/password/pbkdf2_upgrade_plugin_test.py`.

## Locks & vendoring

- The single authoritative lock is `src/Cargo.lock`. `src/librslapd/Cargo.lock` is a stale orphan — cargo ignores it because librslapd is a workspace member; do not update it. (The plugin `*_la_EXTRA` variables in `Makefile.am` also name `src/plugin/<name>/Cargo.lock` files that do not exist.)
- Regenerate the lock intentionally; never hand-edit it. `make -f rpm.mk update-cargo-dependencies` performs a broad `cargo update` on the workspace (`rpm.mk` (`update-cargo-dependencies`)); review the entire `src/Cargo.lock` diff, including transitive version and MSRV changes. For a narrow update, use the same workspace manifest with Cargo's explicit package/version controls (for example `cargo update --manifest-path=./src/Cargo.toml --package <crate> --precise <version>`), then run locked verification. Renovate is one normal source of these updates, not the only permitted one.
- Offline and RPM builds need `make -f rpm.mk download-cargo-dependencies` after a lock change (`cargo vendor` + `cargo fetch` + tar); `dist-bz2` depends on it and ships `vendor/` in the tarball. A dependency bump therefore requires a re-vendor before any offline build.
- The bundled-crates `Provides:` block in `rpm/389-ds-base.spec.in` (between the `Bundled cargo crates list` START/END markers) is machine-written by `rpm/bundle-rust-npm.py` — regenerate it after adding or bumping a crate, never hand-edit it.
- The lock intentionally contains two `base64` versions: 0.23.0 for `pwdchan`, whose code uses the Engine API, and 0.22.1 for `fernet` 0.2.2 (`src/plugins/pwdchan/Cargo.toml` (`base64` dependency), `src/plugins/pwdchan/src/lib.rs`, `src/slapd/Cargo.toml` (`fernet` dependency), `src/Cargo.lock` (`fernet`, `base64` package entries)). When updating either dependency, preserve both selections unless upstream constraints allow them to converge; never remove a lock entry by hand.
